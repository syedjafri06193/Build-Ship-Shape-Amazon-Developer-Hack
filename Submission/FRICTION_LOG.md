# Friction Log: Pantry Chef (Alexa+ track)

These are real issues we hit while building an MCP integration for the Alexa+ track, using the MCP TypeScript SDK 1.32 with Streamable HTTP, Node 22, and macOS.

| # | Task attempted | Steps taken | Expected | Actual | Severity | Workaround | Suggestion |
|---|---|---|---|---|---|---|---|
| 1 | Test the integration in an Alexa+ environment | Looked through the track page and resources for an Alexa+ test console or simulator that accepts an MCP endpoint | A hosted way to point Alexa+ at our `/mcp` URL and talk to it | No Alexa+ test harness for MCP was linked; the track says to "simulate" with your own tools | **High** | Built our own web Alexa+ simulator: an MCP client with Web Speech API voice | Provide a hosted Alexa+ MCP sandbox, even text-only, so every team tests against the same behavior |
| 2 | Understand how Alexa+ selects tools | Searched the docs for guidance on tool naming, descriptions and disambiguation | Guidance on how Alexa+ routes utterances like "next" or "yes" to tools | No Alexa+-specific guidance on tool selection or multi-turn context | **High** | Wrote an Agent Skill (`SKILL.md`) with explicit intent → tool rules, and offered timers as yes/no questions | Publish Alexa+ tool-design guidelines: naming, description length, confirmation patterns, conversational state |
| 3 | Return output that works on voice and screen devices | Looked for a convention for speech vs. visual output in MCP results | A recommended field or pattern for speakable text plus Echo Show visuals | No convention, so every builder will invent their own | Medium | Each tool returns `structuredContent: { speech, data }` and a text block with the speech | Document a standard speech + display response shape for Alexa+ MCP tools |
| 4 | Deploy a scalable Streamable HTTP server | Used `StreamableHTTPServerTransport` in stateless mode (`sessionIdGenerator: undefined`) | One server instance handles all requests | Stateless mode needs a fresh server and transport per request, and GET/DELETE `/mcp` must return 405 by hand | Medium | Built the server per request; kept household state in our own domain layer, keyed by an `x-household` header | Ship a stateless Express helper in the SDK, and show where Alexa+ passes user or household identity |
| 5 | Show expiry as "1 day left" correctly | Computed days left by comparing a local end-of-day time against UTC dates | "Expires tomorrow" shows as 1 day | Showed 2 days because of a UTC vs. local time zone mismatch | Low | Compare normalized ISO dates on both sides | Document the time zone of the Alexa+ user and device in the request context, so servers can do date math correctly |
| 6 | Meet the "license visible in the About section" rule | Put the project in a `Submission/` subfolder that contains its own LICENSE | GitHub shows the license | GitHub only detects a LICENSE at the repo root | Low | Copied LICENSE to the repo root | Mention in the rules that the LICENSE file must be at the repo root |

## Summary
The MCP SDK and Streamable HTTP worked reliably; our end-to-end smoke test passed on the first full run. The biggest gap is on the Alexa+ side: there's no shared simulator, and no guidance on how Alexa+ chooses tools and renders responses. Closing that gap would let builders spend their time on the experience rather than on scaffolding.
